# 客服前后端手动测试用例

## 测试环境

- 前端：<http://127.0.0.1:3000>
- 后端健康状态：<http://127.0.0.1:8001/health>，应返回 `status: ok`、`workflow_ready: true`。
- 演示用户 ID：`bbed30b6-4ffe-48de-9c36-309789bacece`（本地 `udahub.db` 中的 Alice 测试账户）。
- 每次发送都会创建一个新工单。页面会显示工单 ID，测试时记下它以核对后端工具事件。

## 用例

### 1. 主 Agent 普通答复

**输入：** `你好，请用两句话介绍你能帮我处理哪些客服问题。`

**预期：** 页面收到一条自然语言答复，工单最终状态为已完成；没有知识查询、账户查询、澄清或转人工工具结果。

**核对：** 在 `data/core/agent_tickets.db` 的 `ticket_events` 中按工单 ID 查询，不应有 `event_type='llm.tool.result'` 的事件。

### 2. 专家 Agent 委托

分别发送下面两条消息，验证两个专家 Agent 都可被主 Agent 调用：

1. `请查询公共知识库，告诉我 CultPass 关于预订变更的规则；如果没有相关资料，请如实说明。`（公共知识专家）
2. `请查询我当前账户的资料和账户状态，并用一句话总结。`（账户专家）

**预期：** 两次都收到基于对应工具结果的答复，不能把工具 JSON 原样展示给客户。

**核对：** 每个工单至少有一个 `llm.tool.result` 事件，工具名分别包含 `query_public_knowledge` 和 `lookup_current_user_account`。公共知识检索未命中时允许如实报告未找到资料，不要求编造规则。

### 3. 独立澄清

**输入：** `我有个客服问题需要处理，但现在还没说具体是什么。你先帮我处理一下。`

**预期：** 页面直接显示一个面向客户的追问；追问应请求缺少的问题信息，不应继续调用其他工具，也不应在其后再生成主 Agent 的补充答复。

**核对：** 工单的工具结果中有 `ask_clarification`；最终客户答复与澄清问题一致。

### 4. 独立转人工

**输入：** `请帮我取消一笔预订。原因是计划有变，预约编号 TEST-123。`

**预期：**

- Feishu 发送成功时，页面显示“已转人工，等待人工客服回应”，Feishu 测试群收到交接内容；主 Agent 不再追加另一条答复。
- Feishu 发送失败时，页面显示统一安全答复“抱歉，暂时无法完成这一步，请稍后重试。”，不得显示已成功转人工。

**核对：** 工单的工具结果中有 `request_human_handoff`。此用例可能向当前配置的 Feishu 群发送测试交接消息，请只使用测试内容。

## 后端事件核对

将 `<ticket-id>` 替换为页面显示的工单 ID；以下只查看工具名，不读取消息正文：

```sql
SELECT seq, event_type, json_extract(content, '$.name') AS tool_name
FROM ticket_events
WHERE ticket_id = '<ticket-id>' AND event_type = 'llm.tool.result'
ORDER BY seq;
```

普通答复应无结果；专家委托、澄清、转人工应分别看到对应工具名。工具返回的消息事件是判断实际调用路径的依据，不能只凭最终答复内容判断。
