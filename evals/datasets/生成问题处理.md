# DeepEval Golden 生成原理、问题分析与改造方案

## 1. 文档目的

本文说明项目当前使用的 DeepEval Golden 生成原理和执行流程，分析现有问题产生的原因，并整理可行的改造方案。

本文同时记录已实施配置、验证中发现的问题和最终处理方案。固定生成“2 条普通语义问题 + 2 条关键词型问题”的双通道方案已经过小样本验证并完成实施，正式 Golden 和中文检阅表已同步更新。

## 2. 当前环境与使用方式

- DeepEval 版本：`4.2.3`
- 当前入口：`Synthesizer.generate_goldens_from_contexts()`
- 当前输入：知识库中每篇文章的标题与正文合并为一个 `context`，格式为 `Title: <标题>\n\n<正文>`
- 当前输出：每条 Golden 包含 `input`、`expected_output`、`context` 和来源元数据
- 当前数量：每篇文章固定生成 2 条普通语义问题和 2 条关键词型问题，共 4 条
- 当前正式结果：14 篇文章，共 56 条 Golden

项目当前的大致调用关系如下：

```text
知识库文章
  ↓
转换为 contexts
  ↓
DeepEval Synthesizer
  ↓
生成 input
  ↓
过滤与重写
  ↓
问题演化
  ↓
风格重写
  ↓
生成 expected_output
  ↓
组装并导出 Golden
```

## 3. DeepEval Golden 生成流程

### 3.1 初始问题生成

DeepEval 首先根据文章上下文生成候选 `input`。默认提示词的主要要求包括：

- 根据给定 `context` 生成一组 JSON 数据。
- 每条数据包含 `input` 字段。
- `input` 可以是问题，也可以是陈述。
- 尽量生成 `max_goldens_per_context` 指定的数量。
- 不使用上下文之外的知识。
- 默认要求至少包含一条陈述类型的输入。
- 如果提供 `StylingConfig`，则加入 `scenario`、`task` 和 `input_format` 等要求。

默认模板面向通用合成数据，不是专门为客服检索问题设计。因此，它不会天然保证：

- 使用真实用户口吻；
- 一条问题只对应一个场景；
- 问题不包含解决措施；
- 只在适合的文章中生成关键词型问题；
- 所有输入都是用户问句。

### 3.2 质量过滤与重写

初始问题生成后，DeepEval 会使用 critic 模型评估问题质量。

DeepEval 当前默认配置为：

```python
FiltrationConfig(
    synthetic_input_quality_threshold=0.5,
    max_quality_retries=3,
)
```

如果候选问题低于质量阈值，DeepEval 会根据 critic 反馈重写问题。critic 评分时只接收生成的问题，不接收原文章上下文，主要检查问题的自包含性和目标清晰度。当前实现虽然称为过滤，但不会直接删除低分问题；达到最大重试次数后，最后一次重写结果仍会进入后续流程。

这一阶段不会自动理解项目特有的要求，例如“用户口语化”“单一场景”或“关键词问题仅按需生成”。较高阈值还可能促使 critic 将简短的真实用户问题重写得过于具体、专业或自包含。

本项目建议将阈值调低为 `0.3`：

```python
FiltrationConfig(
    synthetic_input_quality_threshold=0.3,
    max_quality_retries=3,
)
```

调整目的：

- 减少 critic 对简短、口语化用户问题的过度重写；
- 保留“为何没看到 CultPass 体验？”这类自然但上下文信息较少的问题；
- 将“单一场景、无解决措施、关键词型问题按需生成”等质量要求交由项目自定义提示词和验收规则控制。

潜在风险：阈值降低后，部分表达模糊或意图不完整的问题也更容易通过。因此必须保留人工抽查，并通过项目侧规则或测试检查问题是否能够映射到明确场景。

### 3.3 问题演化

通过过滤后，DeepEval 默认会对每条问题执行一次演化：

```python
EvolutionConfig(num_evolutions=1)
```

默认候选演化类型包括：

- 推理型；
- 多上下文型；
- 具体化；
- 约束型；
- 比较型；
- 假设场景型；
- 扩展型。

演化的目标是提高问题复杂度和多样性，但它与当前客服检索数据的目标存在冲突。简单问题经过演化后，可能被改成包含多个条件、比较关系或处理步骤的复杂问题。

例如：

```text
适合用户的问题：
为何没看到 CultPass 体验？

复杂化后的问题：
当本地没有 CultPass 体验时，应如何结合地区差异、定位权限、
附近城市以及新城市无内容的情况进行升级处理？
```

因此，现有 Golden 中出现“比较……”“如何结合多个条件……”等专业化表达，不一定全部来自初始提示词，默认演化也可能是重要原因。

### 3.4 风格重写

如果配置了 `StylingConfig`，DeepEval 会在演化后再次重写问题。

可配置字段包括：

```python
StylingConfig(
    scenario=...,
    task=...,
    input_format=...,
    expected_output_format=...,
)
```

各字段作用如下：

| 字段 | 作用 |
|---|---|
| `scenario` | 描述问题产生的业务场景和用户身份 |
| `task` | 描述系统或客服需要完成的任务 |
| `input_format` | 约束问题的语言、语气、结构和格式 |
| `expected_output_format` | 约束期望回答的语言、立场和格式 |

这是 DeepEval 官方提供的主要定制入口，但它只是向默认提示词中追加要求，并没有完全替换底层模板。

### 3.5 期望答案生成

如果 `include_expected_output=True`，DeepEval 会根据最终问题和原文章上下文生成期望答案。

默认期望答案提示词主要要求：

- 使用上下文中的信息回答当前输入；
- 回答简洁、直接；
- 遵守 `expected_output_format` 指定的格式。

默认提示词没有明确要求：

- 站在客服直接回复用户的立场；
- 优先采用文章中的建议话术；
- 隐藏内部授权、升级和审批流程；
- 只回答当前用户场景，不展开全部政策。

因此，默认生成结果容易变成内部规则总结，而不是可直接发送给用户的客服回答。

## 4. 当前生成结果的主要问题及原因

| 问题 | 可能原因 |
|---|---|
| 问题过于专业化 | 默认模板面向通用合成数据；默认演化会增加推理、比较和约束 |
| 一个问题覆盖多个场景 | 模型倾向于尽可能利用整篇上下文；演化可能进一步合并条件 |
| 问题包含解决措施 | 默认模板没有明确禁止把上下文中的处理方案写入问题 |
| 单通道无法稳定控制问题类型配额 | `max_goldens_per_context` 只能控制统一数量，不能保证其中普通语义问题和关键词问题各占多少条 |
| 关键词问题生成策略不准确 | 默认流程不了解关键词/BM25 检索目标，也不知道哪些文章适合关键词型问题 |
| 关键词问题数量不稳定 | 单个 `Synthesizer` 调用无法稳定保证同一文章中普通问题与关键词问题的数量分工 |
| 强化 `StylingConfig` 后仍出现类型混淆 | 小样本中同一文章的两条问题可能都包含相同关键词，没有形成语义与关键词互补 |
| 生成结果泄漏未填充模板 | 小样本出现 `[type of event]`、`[date]`、`[platform/system]` 等占位符；`reservation_id` 字段本身是允许且有价值的检索锚点，不应误删 |
| 标题未进入生成上下文 | 早期实现只把正文传给 Synthesizer，标题仅存在于元数据；现已改为 `Title: <标题>\n\n<正文>` |
| 回答像内部政策说明 | 默认期望答案模板只要求基于上下文回答，没有客服立场约束 |
| 没有优先使用建议话术 | 默认模板不会识别并优先选择文章中的“建议话术” |

## 5. 项目需要的 Golden 生成目标

### 5.1 普通用户问题

- Golden 中的问题使用英文；中文仅用于独立的人工对照材料。
- 使用真实用户视角和日常口语。
- 每条问题只描述一个具体场景和一个主要诉求。
- 问题只描述现象，不包含排查步骤、解决措施、升级条件或政策结论。
- 根据文章中的独立场景拆分问题，不强行把全文内容合并到一个问题中。
- 默认优先生成这种自然语义问题。

### 5.2 关键词型问题

关键词型问题用于补充关键词/BM25 检索测试样本。为减少“是否适合关键词检索”的额外判断和不稳定性，已确认方案不再让 LLM 先做适用性分类，而是每篇文章固定生成 2 条关键词型问题，提供更多候选；不合适的结果后期由人工删除或修改。

每篇文章固定生成：

- 2 条自然、口语化的普通语义问题；
- 2 条自然的关键词型问题。

关键词型问题需要保留原文中有区分度的功能名、状态、错误提示、标准术语或业务标识，但仍必须像用户会发送的一句话。

它的目的包括：

- 提升混合检索中关键词/BM25 通道的召回率；
- 与向量语义检索形成互补；
- 为错误现象、标准术语或关键标识提供精确词项匹配。

关键词型问题优先使用以下检索锚点：

- 包含用户可能直接搜索的功能名、状态名或错误现象；
- 包含有区分度的标准术语，同时用户也可能用口语描述该术语；
- 包含订单号、交易 ID、reservation_id 或错误码等精确标识；
- 仅使用宽泛口语描述时容易与其他文章混淆。

允许自然出现 `reservation_id`、`transaction ID` 等字段，也可以使用不对应真实用户的合理虚构值，例如 `RES-12345`。需要过滤的是 `[type of event]`、`[date]`、`[platform/system]` 等未填充模板，而不是业务字段本身。即使每篇文章都固定生成关键词问题，也不得机械堆叠无关业务词。

### 5.3 期望回答

- Golden 中的期望回答使用英文；中文翻译不得写回正式 JSONL。
- 使用客服直接面向用户的口吻。
- 只回答当前问题对应的场景。
- 原文章的建议话术可以回答问题时，优先采用建议话术。
- 明确告诉用户下一步需要提供什么或执行什么。
- 不直接暴露内部授权、审批或升级流程。
- 不承诺原文章未授权的退款、补偿、处理结果或时效。
- 所有信息必须由原文章支持。

## 6. 可行的修改方式

### 6.1 方案一：使用 DeepEval 官方配置

通过 `StylingConfig` 增加客服业务约束，并通过 `EvolutionConfig` 关闭问题演化。

示例：

```python
from deepeval.synthesizer import Synthesizer
from deepeval.synthesizer.config import (
    EvolutionConfig,
    FiltrationConfig,
    StylingConfig,
)

styling_config = StylingConfig(
    scenario=(
        "真实 CultPass 用户向客服咨询自己遇到的具体问题。"
        "用户使用自然、口语化表达，不使用客服内部术语。"
    ),
    task=(
        "根据知识文章生成客服检索测试数据。"
        "每条问题只描述一个具体用户场景，不包含解决措施。"
        "默认生成普通口语问题；仅当文章确实适合关键词检索时，"
        "才补充自然的关键词型问题。"
    ),
    input_format=(
        "一条简短的英文用户消息。"
        "使用第一人称或自然疑问句，不包含答案提示、排查步骤、"
        "授权条件或升级处理方案。"
    ),
    expected_output_format=(
        "一段客服直接回复用户的英文回答。"
        "只回答当前场景；优先采用上下文中的建议话术；"
        "明确用户下一步动作；不暴露内部授权或升级流程。"
    ),
)

synthesizer = Synthesizer(
    model=model,
    filtration_config=FiltrationConfig(
        synthetic_input_quality_threshold=0.3,
        max_quality_retries=3,
    ),
    styling_config=styling_config,
    evolution_config=EvolutionConfig(num_evolutions=0),
)
```

#### 为什么建议 `num_evolutions=0`

关闭 evolution 是为了避免问题在初始生成后又被随机改成推理型、比较型、多条件或假设型问题。

该设置只跳过问题演化，不会关闭：

- 基于上下文生成问题；
- 质量过滤；
- 风格重写；
- 期望答案生成。

这不是 DeepEval 的通用最佳配置，而是针对当前“真实客服检索问题”目标的选择。如果未来需要评估复杂推理，可以单独生成一批启用 evolution 的数据，不与日常客服检索 Golden 混合。

#### 优点

- 使用官方公开接口；
- 改动范围小；
- 不修改第三方安装包；
- 容易验证和回退。

#### 局限

- 默认底层模板仍然存在；
- 默认模板要求输入可以是问题或陈述，甚至要求至少包含一条陈述；
- 关键词型问题是否适合某篇文章，需要模型自行判断，稳定性有限；
- `max_goldens_per_context` 仍然是统一上限，不能精确表达每篇文章需要不同数量的问题；
- 复杂规则全部写入 `StylingConfig` 后，模型不一定能够稳定遵守。

### 6.2 方案二：项目侧固定双通道生成

不再要求一次 DeepEval 调用自行分配问题类型，而是在项目侧明确执行两个独立通道：

```text
标题 + 正文
  ├─ 普通问题通道：生成 2 条 semantic 问题
  └─ 关键词问题通道：生成 2 条 keyword 问题
       ↓
合并、去重、校验、生成 expected_output
```

两个通道可以继续复用 DeepEval 的模型适配、过滤配置、`Golden` 数据结构和期望答案生成能力，但分别使用不同的 `StylingConfig`：

- 普通问题通道只强调真实用户口吻、单一场景和不包含解决措施；
- 关键词问题通道要求自然保留标题或正文中的功能名、状态、错误提示、标准术语或业务标识；
- 不再额外调用 LLM 判断文章是否适合关键词检索；
- 每篇文章固定产出 2 条普通问题和 2 条关键词问题；
- 价值较低或表达生硬的关键词问题由后期人工删除或修改。

该方案比“LLM 先判断文章是否适合，再决定是否生成关键词问题”简单，也能稳定控制样本数量并提供更多筛选候选。代价是部分文章的关键词问题可能不够自然，需要人工复核。

#### `input_type` 字段

可选地在每条 Golden 顶层增加：

```json
"input_type": "semantic"
```

或：

```json
"input_type": "keyword"
```

`input_type` 描述当前问题的生成类型，因此适合放在 Golden 顶层，而不是描述来源文章的 `additional_metadata` 中。它可用于人工筛选、验证每篇文章是否满足 2+2 配额，以及分别统计向量检索和 BM25 检索效果。但该字段会改变现有 JSONL 结构，因此是否添加仍需用户确认；不添加也不影响双通道生成本身。

### 6.3 方案三：直接修改或运行时替换 DeepEval 模板

直接修改或 monkey patch DeepEval 的 `SynthesizerTemplate` 可以替换底层提示词，但会依赖第三方内部实现。升级或重装依赖后修改可能丢失，运行时替换还可能影响进程内其他 Synthesizer 调用。

不选择该方案，因为维护风险高、版本兼容性差，也不利于测试和代码审查。

## 7. 当前结论与实施状态

### 7.1 方案一的验证结论

方案一已经能够较好地控制普通语义问题和客服式期望回答，当前已采用的配置包括：

- `StylingConfig` 约束英文用户口吻和客服回答；
- critic 阈值为 `0.3`；
- `EvolutionConfig(num_evolutions=0)`；
- context 使用 `Title: <标题>\n\n<正文>`。

但是，尝试进一步通过同一个 `StylingConfig` 强制“1 条语义问题 + 1 条关键词问题”时，小样本验证失败：

- 同一文章的两条问题可能都变成关键词问题；
- 两条问题可能使用相同检索锚点，缺少互补性；
- 出现 `[type of event]`、`[date]`、`[platform/system]` 等未填充模板。

失败样本保存在 `evals/datasets/retrieval_goldens_keyword_trial.jsonl`。正式 Golden 未被该试验覆盖，生成脚本也已恢复到此前通过验证的配置。

### 7.2 推荐的下一步

采用方案二的固定双通道生成：每篇文章生成 2 条普通语义问题和 2 条关键词型问题，不进行关键词适用性判断，后期人工删除或修改不合适的问题。

该方案的主要理由：

- 不依赖 LLM 稳定执行同批次问题的类型分工；
- 不需要增加一次“是否适合关键词检索”的判断调用；
- 数量固定，容易测试和人工检查；
- 能确保 BM25 通道始终有关键词测试样本；
- 符合当前数据量较小、允许人工复核的工作方式。

### 7.3 实施结果

方案二已完成实施。小样本通过后，正式 `retrieval_goldens.jsonl` 已更新为 56 条，中文检阅表已同步。`input_type` 未获得明确确认，因此正式 JSONL 保持原字段结构；中文检阅表根据生成通道显示“普通语义/关键词”类型。实现没有修改 `site-packages` 中的 DeepEval 源码。

## 8. 验证方案

### 8.1 问题验证

- 是否像真实用户会直接发送给客服的一句话？
- 是否只表达一个主要场景？
- 是否没有解决措施、排查步骤和内部流程？
- 是否由原文章直接支持？
- 每篇文章是否生成 2 条普通语义问题和 2 条关键词型问题？
- 如果生成关键词型问题，关键词是否自然、有区分度且与原文匹配？
- 关键词问题是否允许自然使用 `reservation_id`、`transaction ID` 等业务字段？
- 是否不存在 `[date]`、`[type of event]`、`[platform/system]` 等未填充模板？
- 同一文章的三条问题是否没有重复或近似重复？

### 8.2 期望回答验证

- 是否使用客服直接面向用户的口吻？
- 是否只回答当前问题？
- 是否优先使用了适用的建议话术？
- 是否明确给出用户下一步动作？
- 是否隐藏不应直接暴露的内部流程？
- 是否没有引入原文之外的信息或承诺？

### 8.3 自动化测试建议

- 验证输出 JSON 结构和必填字段。
- 验证问题和答案均为非空字符串。
- 验证每条 Golden 能关联回正确的文章 ID。
- 验证没有重复问题。
- 验证每篇文章具有 2 条普通语义问题和 2 条关键词型问题；如果不增加 `input_type`，则需要在生成阶段使用其他内部标记完成该检查。
- 使用正则拦截未填充的方括号模板，但不得把 `reservation_id` 等普通业务字段误判为非法占位符。
- 验证关键词型问题至少包含一个来自标题或正文的检索锚点。
- 使用固定假模型测试提示词参数和组装逻辑。
- 对代表性文章建立人工认可的快照测试。
- 如果确认增加 `input_type`，验证其值只能为 `semantic` 或 `keyword`。

## 9. 确认与实施状态

已确认事项：

1. 正式 Golden 的问题和回答使用英文，中文仅保存在独立对照材料中。
2. context 包含文章标题和正文。
3. `reservation_id`、`transaction ID` 等字段允许自然出现在问题中，也允许使用合理的虚构值。
4. 不再增加 LLM 调用来判断文章是否适合关键词检索，统一生成 2 条普通语义问题和 2 条关键词型问题，后期人工调整。

实施状态：

1. 已将单通道生成流程改为固定 2+2 的双通道生成流程。
2. 正式 Golden 顶层未增加 `input_type`，保持现有字段兼容性；类型仅在生成阶段内部区分，并在中文检阅表中展示。
3. 小样本通过后，已覆盖正式 `retrieval_goldens.jsonl` 并同步更新中文检阅表。
