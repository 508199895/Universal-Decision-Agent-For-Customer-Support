# Agent 什么时候值得调用工具？

## 先说结论

Agent 调用工具的价值，主要在于它能根据用户的话和已经拿到的信息，临时判断接下来该怎么做。

如果一开始就能明确要不要调用、调用哪个工具、按什么顺序调用、参数填什么，那么通常直接用固定程序执行更简单，也更稳定。

## 和固定程序有什么不同？

固定程序的步骤预先写好。例如：收到订单号后，调用订单接口，再把结果展示出来。每次都按同一套规则运行。

Agent 则会根据具体情况作判断。它可能先查订单；看到订单已发货后再查物流；如果订单尚未发货，就转而检查库存或向用户说明情况。后续步骤取决于前一步的结果。

## 哪些不确定性会让 Agent 有用？

| 场景 | 描述 |
|---|---|
| 是否需要调用工具尚不明确 | 当前节点需要判断用户的问题能否直接回答，还是必须查询本地数据或执行操作。例如，用户问“为什么我的订单还没到”，需要判断是否先查订单状态。 |
| 可选工具不止一个，需要模型选择 | 当前节点需要根据用户意图，在多个本地工具中挑选合适的工具。例如，根据订单状态选择查询物流、库存或退款记录。 |
| 工具调用顺序取决于上下文或前一步结果 | 当前节点无法预先固定完整调用顺序，需要根据查询结果决定下一步。例如，先查订单；若已发货，再查物流。 |
| 工具参数需要从自然语言或非结构化信息中识别 | 当前节点需要从用户表达、对话上下文或文档中提取参数。例如，把“下周二下午”转换为明确的日期和时间范围。参数应在真正需要理解它的节点识别；如果前置节点已经产出结构化参数，后续节点直接传递即可。 |

这些判断越多、越依赖具体上下文，Agent 越能发挥作用。反过来，如果每一步都已明确，Agent 就不必参与每次工具调用。

## 从 Agent 判断切换到固定执行

可以把过程想成“先弄清楚，再照章办理”：

1. Agent 理解用户要解决什么问题。
2. Agent 判断需要哪些工具、先后顺序和调用参数。
3. 一旦步骤和参数明确，程序按固定规则校验并执行。
4. 程序返回结果；只有出现新情况或原计划走不通时，才再让 Agent 判断下一步。

例如，用户说“帮我看看这笔订单为什么没到”：Agent 先判断要查订单和物流；拿到订单号并确认订单已发货后，程序按固定流程查询物流状态、检查返回值并生成结果。若物流信息异常或查不到，再由 Agent 决定是否换路径或向用户提问。

## 简单判断

**如果还不确定要不要调用工具、该用哪个工具、调用顺序或参数，Agent 就有价值。等这些事情明确后，固定程序通常更合适。**

也就是说，Agent 主要负责替我们想清楚“该怎么查、怎么做”；明确的步骤则交给程序可靠地完成。

## 本地工具适合交给 Agent 调用的条件

| 场景 | 描述 |
|---|---|
| 需要模型识别参数的工具 | 需要模型识别参数【甚至得是在对应节点使用，如果是后续节点使用，就没必要了，完全可以确定性调用】 |
| 需要模型选择的工具集 | 需要模型选择的工具集【是否调用&调用顺序很】 |
