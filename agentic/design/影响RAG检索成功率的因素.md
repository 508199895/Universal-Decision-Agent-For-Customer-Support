# 影响 RAG 检索成功率的因素

RAG 的检索成功率通常是指：**正确答案对应的证据是否出现在 Top-K 检索结果中**。常用指标是 `Recall@K`。

检索成功并不只由检索算法决定。知识覆盖、文档解析、文档切分、查询处理、元数据过滤、召回策略和重排序都会影响最终结果。

## 影响因素总览

| 类别 | 影响因素 | 典型问题 | 优化方式 |
| --- | --- | --- | --- |
| 数据质量 | 文档完整性、准确性、时效性 | 知识库没有答案，文档过期或互相冲突 | 补齐数据源、版本管理、增量更新、重复与冲突检测 |
| 文档解析 | 正文、标题、表格、图片是否正确提取 | PDF 乱码、表格结构丢失、扫描件没有 OCR | 版面解析、OCR、按文件类型选择解析器、人工抽检 |
| 文档切分 | 块大小、重叠、语义边界、层级结构 | 答案被切断、块太大导致噪声、标题与正文分离 | 结构化切分、父子分块、适度重叠、标题注入 |
| 查询处理 | 查询改写、纠错、指代补全、问题拆解 | 用户表述过短、多轮指代不清、一个问题包含多个条件 | 查询改写、对话补全、Multi-Query、问题拆解 |
| 检索策略 | BM25、向量检索、混合检索、过滤条件 | 精确编号搜不到、同义表达匹配不到、过滤错误 | 混合检索、动态权重、元数据过滤、扩大候选集 |
| 排序与过滤 | Top-K、重排、去重、业务权重 | 正确内容已召回但排名太低，重复内容占满结果 | Reranker、去重、时效性与权威性加权、动态 Top-K |

## 1. 知识覆盖和数据质量

如果正确答案根本不在知识库中，调整 Embedding、Top-K 或重排模型都没有意义。

常见问题：

- 文档没有同步或同步失败；
- 只同步了正文，没有同步附件；
- 知识已经过期；
- 同一制度存在多个冲突版本；
- 答案只存在于图片、表格或扫描 PDF 中；
- 正确内容被权限规则意外排除。

建议关注以下指标：

- 知识覆盖率；
- 文档更新时间；
- 数据同步成功率；
- 无答案问题占比；
- 权限过滤前后的召回差异。

## 2. 文档解析质量

原始文档中存在答案，不代表解析和索引后的文本中仍然存在可检索的答案。例如，错误换行可能把“3～5 个工作日”解析成多个无关联的文本片段，导致关键词检索、向量表示和重排同时受到影响。

重点检查：

- PDF 是否出现错误换行或乱码；
- 表格的行列关系是否保留；
- 标题是否与正文关联；
- 图片文字是否经过 OCR；
- 页眉和页脚是否大量混入正文；
- 列表编号和步骤顺序是否正确；
- 特殊符号、产品型号和错误码是否损坏。

## 3. 文档切分方式

切分决定检索系统能够看到怎样的知识单元，也会同时影响关键词匹配、向量表示和重排效果。

| 切分问题 | 对检索的影响 |
| --- | --- |
| 块太小 | 上下文不足，无法表达完整语义和适用条件 |
| 块太大 | 无关内容稀释核心语义，向量表示不够聚焦 |
| 没有重叠 | 跨边界信息容易丢失 |
| 重叠过大 | 重复结果占满 Top-K |
| 标题与正文分开 | 正文失去产品、业务或章节语境 |
| 表格逐行切开 | 表头、条件和数值失去关联 |
| 固定字符切分 | 条款、步骤和问答容易被截断 |
| 所有文档使用相同策略 | 无法适应制度、FAQ、手册和表格等不同结构 |

建议：

- 优先按章节、标题和段落切分；
- 为每个块附带完整标题路径；
- 对长章节进行二次切分；
- 建立父块与子块的关联；
- 表格切分时保留表头；
- FAQ 将“问题＋答案”作为一个完整块；
- 条款保留适用条件、例外情况和处理结果；
- 通过评估集确定块大小和重叠范围，不机械使用固定参数。

## 4. 查询与文档的表达差异

用户语言通常更加口语化，而知识文档倾向于使用正式术语。例如，用户询问“钱什么时候回来”，文档可能写成“退款预计在审核通过后 3～5 个工作日原路退回”。向量检索更擅长处理这种同义表达。

反过来，错误码、订单号和产品型号需要精确匹配，单纯向量检索可能召回大量主题相似但并不准确的内容。

| 查询类型 | 更适合的方法 |
| --- | --- |
| 自然语言、同义表达 | 向量检索 |
| 订单号、错误码、产品型号 | 关键词检索或精确匹配 |
| 自然语言与专有名词混合 | 混合检索 |
| 多条件复杂问题 | 查询拆解 |
| 表述模糊或过短 | 查询改写、Multi-Query |
| 多轮对话中的指代 | 结合对话历史补全查询 |

## 5. Embedding 模型和向量配置

Embedding 决定查询和文本块如何映射到向量空间。主要影响因素包括：

- 模型是否支持中文和多语言；
- 模型是否适合当前业务领域；
- 模型是否适合当前文本长度；
- 查询和文档是否需要使用不同前缀；
- 是否正确执行向量归一化；
- 向量距离计算方式是否正确；
- 文本是否因超过模型长度限制而被截断；
- 文档索引和查询是否使用同一模型及同一版本。

常见配置错误：

- 文档已使用新模型重新向量化，但查询仍使用旧模型；
- 模型要求添加 `query:` 和 `passage:` 前缀，但系统没有添加；
- 答案位于长文本尾部，在向量化前已被截断；
- 中文业务使用了中文能力不足的模型；
- 标题、导航、页脚和正文未经清洗便一起向量化。

## 6. 检索策略

### 向量检索

向量检索能处理同义表达和语义相似问题，但对数字、日期、型号、错误码、人名和精细业务条件可能不稳定。

### BM25 关键词检索

BM25 适合精确词语和标识符匹配，但容易漏掉同义词、缩写和口语表达。

### 混合检索

生产系统通常组合向量检索与 BM25：

```text
向量检索结果 ─┐
                ├─ 合并与去重 ─> Reranker ─> Top-K
BM25 检索结果 ─┘
```

还可以加入：

- 元数据过滤；
- 产品或业务线过滤；
- 时间范围过滤；
- 权限过滤；
- 权威来源加权；
- 新版本和生效版本加权。

## 7. 查询处理

用户原始查询不一定适合直接检索。以下情况需要预处理：

- 多轮对话中的“它”“上一个”等指代缺少上下文；
- 查询太短，缺少产品、地区或时间范围；
- 一个查询同时包含多个子问题；
- 用户使用错别字、缩写或非标准产品名称；
- 用户表达的是业务意图，而不是文档中的专业术语。

常见处理方式：

- 拼写纠正和术语标准化；
- 基于对话历史生成独立、完整的查询；
- 将复杂问题拆成多个子查询；
- 生成多个不同表述的查询，即 Multi-Query；
- 提取产品、时间、地区、版本等实体和约束；
- 保留错误码、型号等关键字符串，避免改写过程中丢失。

## 8. 元数据与过滤条件

过滤可以显著提升精度，但错误的过滤条件会直接导致零召回。例如，用户查询企业版功能，但系统错误添加了“个人版”的产品过滤条件，那么正确资料不可能进入候选集。

常见问题：

- 产品名称和标签不统一；
- 部门或业务分类错误；
- 时间范围设置过窄；
- 权限字段配置错误；
- 新旧版本标签缺失；
- 查询理解错误，选择了错误的过滤条件。

建议：

- 权限约束必须使用硬过滤；
- 产品、时间和业务分类可以根据场景采用软过滤或加权；
- 严格过滤无结果时，在安全允许的范围内扩大检索范围；
- 记录过滤前后的候选数量和结果，便于定位问题；
- 统一元数据字段、枚举值和命名规则。

## 9. 候选数量 Top-K

Top-K 太小，正确内容容易被漏掉；Top-K 太大，则会增加重排延迟、模型成本、重复结果和上下文噪声。

应区分两个 K：

| 参数 | 含义 | 示例范围 |
| --- | --- | --- |
| 召回 K | 初检阶段返回的候选数量 | 20～100 |
| 生成 K | 重排后提供给生成模型的数量 | 3～10 |

典型流程是：

> 初检召回 50 个候选 → 去重 → 重排 → 选取前 5 个上下文

具体数值必须通过业务评估集确定，不能机械套用示例范围。

## 10. Reranker 重排序

重排用于提高候选结果的排序精度，适合解决以下问题：

- 正确块已召回，但排名靠后；
- 多个文本主题相似，但适用条件不同；
- 向量检索只能判断主题相似，不能准确判断是否回答了问题；
- 关键词命中了大量包含相同词语但语义无关的内容。

重排无法补救初检漏召回：如果正确证据没有进入重排候选集，Reranker 无法凭空找回它。

因此需要分别评估：

- 初检阶段的 `Recall@20` 或 `Recall@50`；
- 重排后的 `Recall@3`、`Recall@5`；
- 重排前后的 MRR 或 NDCG；
- 重排延迟和单次调用成本。

## 11. 去重与结果多样性

如果 Top-5 都是同一篇文档的相邻重复块，即使检索分数很高，也可能遗漏回答问题所需的其他证据。

处理方式：

- 根据文档 ID 和内容相似度去重；
- 限制每篇文档最多进入多少个块；
- 使用 MMR 增加结果多样性；
- 将相邻且连续的文本块合并；
- 同一知识的多个版本只保留当前权威版本；
- 对需要多份证据的问题进行子问题级检索。

## 12. 权限、版本和时效性

企业级 RAG 中，权限与版本控制既关系安全，也直接影响检索成功率。

常见问题：

- 用户无权限访问正确文档；
- 新旧制度同时被召回；
- 草稿文档排名高于正式文档；
- 已撤销文档仍然留在索引中；
- 文档更新后旧向量没有删除；
- 检索到适用于其他地区、客户等级或时间段的规则。

建议为每个文本块记录：

- 文档 ID 和文本块 ID；
- 文档版本；
- 生效和失效时间；
- 发布状态；
- 来源系统；
- 权威级别；
- 产品、业务线和地区；
- 用户、角色或部门权限。

## 检索失败的定位方法

| 检查结果 | 最可能的问题 |
| --- | --- |
| 原始知识库中没有答案 | 数据覆盖问题 |
| 原文有答案，但解析文本中没有 | 解析或 OCR 问题 |
| 解析文本有答案，但被分散到多个块 | 切分问题 |
| 使用答案原文搜索仍然找不到 | 索引或检索配置问题 |
| BM25 能找到，向量检索找不到 | Embedding 或语义表示问题 |
| 向量检索能找到，BM25 找不到 | 用户表达与文档措辞不同 |
| 正确块在 Top-50，但不在 Top-5 | 初始排序或重排问题 |
| 添加过滤条件后找不到 | 元数据或过滤条件问题 |
| 正确块已在 Top-5，但最终回答错误 | 上下文组装、Prompt 或生成问题 |

## 推荐的排查与优化顺序

1. 确认原始知识库中是否存在正确答案；
2. 检查文档是否被正确解析；
3. 检查答案是否被合理切分并保留必要上下文；
4. 检查元数据、权限、版本和过滤条件；
5. 使用标准问题集评估初检 `Recall@K`；
6. 优化查询改写、Embedding 和混合检索；
7. 在高召回候选集上优化重排；
8. 最后优化去重、上下文组装、Prompt 和生成模型。

整体优先级可以概括为：

> **知识覆盖 → 解析质量 → 文档切分 → 元数据 → 查询处理 → 初检召回 → 重排序 → 上下文组装**

核心原则是：**不要只观察最终回答是否正确，而要确认正确证据在哪一步消失。** 初检需要保证高召回，重排需要保证高精度；如果正确内容没有进入候选集，后续重排和生成都无法有效补救。
